# Развёртывание лидгена в Timeweb Cloud

Решение принято: **Москва + перенос писателя на Kimi** (весь пайплайн в РФ, Claude из прод-пути
убирается). Объём — 50–200 компаний за прогон, регулярно.

---

## 0. Почему именно так (чтобы не переигрывать потом)

**Россия не входит в список поддерживаемых стран Anthropic**
([anthropic.com/supported-countries](https://www.anthropic.com/supported-countries) — Казахстан,
Германия, Нидерланды есть, России нет). А Claude в текущем пайплайне делает 2 из 3 деливераблов
(карта бизнес-процессов, карта ролей) плюс LLM-экстракцию в движке ресёрча. Значит сервер в
Москве с текущим кодом не заработает — упрутся именно эти стадии.

Дополнительно: у нас **нет API-ключа Anthropic** (биллинг — подписка Max). Подписочная авторизация
на headless-сервере потребовала бы OAuth-токена и всё равно упёрлась бы в гео-ограничение. То есть
Claude на прод-сервере в РФ не жилец по двум независимым причинам.

Отсюда выбранный путь: **прод-пайплайн полностью на Kimi** (эндпоинт `gpllmkeeper.dtc.tatar` —
проверено: публично доступен по HTTPS, отвечает `401` без ключа, IP 185.104.107.128). Claude
остаётся только для локального разговорного `orchestrator_agent.py`, в Docker он не используется
(ENTRYPOINT — `orchestrator.py`).

## 1. Конфигурация сервера

| Параметр | Значение | Почему именно так |
|---|---|---|
| Услуга | **Облачный сервер** (не Apps/PaaS) | Нужен Docker-хост с Xvfb, headed-Chrome и постоянным томом. PaaS это не даст. |
| Локация | **Москва** | Все внешние сервисы российские: RusProfile, Яндекс Диск, Dadata/Checko, ГИР БО, Kimi-шлюз ЦИТ РТ. |
| Архитектура | **x86-64, только** | `Dockerfile` ставит `google-chrome-stable` из репозитория Google — он **amd64-only**, arm64-сборки нет. У Timeweb ARM и так нет, но при выборе конфигуратора это ограничение помнить. |
| vCPU | **8** | Пик: 2 компании параллельно (`--workers 2`) × краул `DR_CRAWL_CONCURRENCY=4` = 8 одновременных фетчей, плюс до 2 chromium на рендер PDF. Chromium в бурстах упирается в CPU. |
| RAM | **16 ГБ** (минимум 12) | Расчёт ниже. |
| Диск | **100–120 ГБ NVMe** | Образ тяжёлый: Chrome + два chromium (основной venv и Kimi-venv) + Crawl4AI с onnxruntime ≈ 6–8 ГБ. Остальное — `/data`: лиды, .docx, .pdf, кэш находок. |
| ОС | **Ubuntu 24.04 LTS** | Базовый образ `python:3.12-slim-bookworm` тянется в Docker, хосту нужен только свежий Docker. |
| Сеть | Выделенный **публичный IPv4** (180 ₽/мес) | Постоянный IP важен для стабильности сессии RusProfile. |
| Бэкапы | Включить (6 ₽/ГБ/мес) | В `/data` лежат куки RusProfile и результаты — потерять их дорого. |
| Оплата | Почасовая | Первые дни — тест антибота на «часовом» сервере, до оплаты месяца. |

Опубликованный тариф-ориентир: **8 vCPU / 12 ГБ / 100 ГБ NVMe — 2772 ₽/мес**
([timeweb.cloud/services/cloud-servers](https://timeweb.cloud/services/cloud-servers)). 16 ГБ
собирается в конфигураторе — он позволяет менять CPU/RAM/диск независимо.

### Откуда 16 ГБ

Пиковое потребление при `--workers 2` (дефолт):

| Компонент | RAM |
|---|---|
| Python + зависимости Crawl4AI (onnxruntime, numpy, nltk, magika) | 1,0–1,5 ГБ |
| Краул: chromium × 2 компании (по 4 потока в каждой) | 2,0–3,0 ГБ |
| One-pager: 2 × (python Kimi-venv + chromium), `ORQ_ONEPAGER_CONCURRENCY=2` | 1,2–1,6 ГБ |
| Фаза 1: headed-Chrome под RusProfile (последовательно, не пересекается с Фазой 2) | 0,6–0,8 ГБ |
| `shm_size: 2gb` из docker-compose (tmpfs — ест RAM) | 2,0 ГБ |
| Запас под `ORQ_MIN_RAM_GB=2.5` (бэкпрешер, иначе прогон встанет в ожидание) | 2,5 ГБ |

Итого пик ≈ 9–11 ГБ. На 12 ГБ прогон поедет, но бэкпрешер будет постоянно притормаживать; на 16 ГБ
появляется запас поднять `--workers` до 3–4. Плюс **swap 4 ГБ** на хосте — страховка от OOM-killer,
который иначе убьёт chromium посреди компании.

## 2. Порядок развёртывания

### Шаг 1. Проект и сервер
1. В панели Timeweb создать **проект** (`leadgen`) — он группирует сервер, диск, бэкапы и сеть.
2. Создать **облачный сервер**: Москва, Ubuntu 24.04 LTS, 8 vCPU / 16 ГБ / 100 ГБ NVMe,
   публичный IPv4, SSH-ключ (не пароль).
3. Файрвол: входящий — **только SSH (22)** со своего IP. Пайплайн — батч-джоба, входящих
   подключений не требует.

### Шаг 2. Хост
```bash
apt update && apt install -y docker.io docker-compose-plugin git
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

### Шаг 3. Код и секреты
```bash
git clone <репозиторий> /opt/lead_gen && cd /opt/lead_gen
```
Секреты — в файл `/opt/lead_gen/.env` с правами `600` (root), а не в переменные окружения шелла:
```
KIMI_API_KEY=...
KIMI_BASE_URL=https://gpllmkeeper.dtc.tatar/v1
KIMI_MODEL_NAME=kimi-k2.7-code
YANDEX_DISK_TOKEN=...
DADATA_TOKEN=...
CHECKO_TOKEN=...
```
`docker compose` подхватит его сам. `ANTHROPIC_API_KEY` на сервере **не нужен** — Claude из
прод-пути убран.

### Шаг 4. Сборка
```bash
docker compose build
```
Сборка сама себя проверяет: `py_compile`, офлайн-прогон `test_deep_research.py`,
`apply_patches.py --check` и импорт стадии one-pager. Если образ собрался — окружение согласовано.

### Шаг 5. ⚠️ Куки RusProfile — сделать ДО первого прогона
`_collect` падает с `SystemExit`, если нет файла куки (`orchestrator.py:362`), а `--login` требует
интерактивного браузера — на headless-сервере его нет. Варианты:
- скопировать `.rp_cookies.json` с рабочей машины в `./docker-data/rusprofile/cookies.json`;
- либо один раз залогиниться на сервере через Xvfb + x11vnc и пробросить порт по SSH.

Профиль Chrome с Windows на Linux **не переносится** — рассчитывать надо на куки-файл.

## 3. Главный риск — и его надо проверить первым

**Антибот RusProfile против IP дата-центра.** Проверено: голому `curl` RusProfile отдаёт **403**.
Пайплайн обходит это headed-Chrome через `undetected-chromedriver` — но с домашнего IP. IP
московского дата-центра Timeweb — это по-прежнему IP дата-центра, и он опознаётся антиботом
гораздо охотнее.

Это риск **не от хостинга, а от репутации IP**, и переезд в другую локацию его не лечит. Поэтому
порядок такой:

1. Поднять сервер **на почасовой оплате**.
2. Прогнать Фазу 1 на 5–10 компаниях.
3. Смотреть на результат:
   - проходит → фиксируем конфигурацию, оплачиваем месяц;
   - ловим капчу/блок → нужен **резидентный или мобильный прокси** под Фазу 1 (только под неё:
     остальные стадии ходят по API и прокси не требуют).

Не переходить к переносу писателя на Kimi, пока этот пункт не закрыт: если Фаза 1 не собирает
лидов, остальное неважно.

## 4. Перенос писателя на Kimi (после шага 3)

Claude сейчас завязан в четырёх файлах:

| Файл | Что делает | Судьба |
|---|---|---|
| `orchestrator_agent.py` | разговорная обёртка (Claude SDK) | **остаётся локальной** — в Docker не используется |
| `orchestrator.py` (`_research_one`) | сессия писателя + тулы `save_*_docx` | переносится |
| `company_research_agent.py` | схемы `PROCESS_MAP_SCHEMA` / `ROLES_CONTACTS_SCHEMA` + рендер .docx | схемы остаются, рендер остаётся (чистый Python) |
| `deep_research_engine.py` | LLM-экстракт и критик (`DR_EXTRACT_MODEL=sonnet`, `DR_LLM_CONCURRENCY=2`) | переносится |

**Ключевое упрощение.** Тул-колл-цикл Claude существует ровно для одного: загнать структурированные
данные в детерминированные питоновские рендереры `_write_process_map_docx` / `_write_roles_contacts_docx`.
Значит на Kimi агент с тулами не нужен вовсе — достаточно попросить **строгий JSON по той же
схеме** и скормить его существующим рендерерам. Это ровно тот приём, что уже работает в
`onepager_kimi.py` («ответь только HTML»), только «ответь только JSON». Плюсы: нет `yolo`, нет
агентного цикла на более слабой модели, результат детерминированно валидируется по схеме.

Побочный эффект: если Claude уходит с сервера полностью, исчезает и конфликт `pydantic-core` —
два venv в образе можно схлопнуть в один. Делать это стоит **после** того, как перенос заработает,
отдельным шагом.

⚠️ Честно про качество: `kimi-k2.7-code` — модель под код. На аналитических .docx она почти
наверняка слабее Opus. Перед переключением прода прогнать 3–5 компаний и сравнить с текущими
файлами глазами.

## 5. Чего на сервере не будет

- `ANTHROPIC_API_KEY` — не нужен.
- Входящих портов, кроме SSH.
- Windows-специфики: блокировка сна (`SetThreadExecutionState`), `pywin32`, пути `D:\лиды` —
  всё перекрыто переменными `ORQ_DATA_ROOT=/data`, `ORQ_LEADS_DIR=/data/leads`,
  `RUSPROFILE_*=/data/rusprofile/...` (проверено: код эти переменные читает).
