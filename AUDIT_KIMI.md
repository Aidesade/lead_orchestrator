## 1. Зависимости

### Основной venv — в порядке
`lead_orchestrator/requirements.txt`: **130 пакетов, все прибиты через `==`**, непинованных строк
нет. Ключевые: `claude-agent-sdk==0.2.103`, `playwright==1.60.0`, `undetected-chromedriver==3.5.5`,
`Crawl4AI==0.9.0`, `python-docx==1.2.0`, `pywin32==311` (в Linux вырезается `Dockerfile:35-42`).

### Kimi-venv — здесь и был корень проблемы

Исходное состояние: отдельного `requirements.txt` не было вовсе. Источников истины два, и они
противоречили друг другу и реальности:

| Источник | kimi-cli | playwright |
|---|---|---|
| `Dockerfile` (было) | не пинован → резолвер даёт **1.12.0** | 1.60.0 |
| `README` (было) | не пинован, плюс совет `pip install --upgrade kimi-cli` | без версии |
| Фактический `.venv_kimi` (было) | **1.48.0** | 1.61.0 |

**Ключевой факт, который я сначала понял неверно** (первая редакция этого аудита утверждала,
что верхней границы нет — это ошибка, её вскрыл `pip`):

> `kimi-agent-sdk 0.0.5` объявляет **`kimi-cli>=1.12.0,<1.13.0`**.

Граница есть, и она осмысленная: SDK зовёт `KimiCLI.create(..., skills_dir=...)` — имя параметра
из 1.12.x. В `kimi-cli >=1.4x` параметр переименован в `skills_dirs` (список). То есть
`kimi-cli 1.48.0` в venv стоял **вопреки** объявленной совместимости (README прямо советовал
`pip install --upgrade kimi-cli`), а разрыв API закрывали вторым патчем в `site-packages`.

### 🔴 Следствие: Docker собирал заведомо нерабочий образ

Проверено прогоном, не рассуждением:

1. Строка из `Dockerfile` — `pip install kimi-agent-sdk==0.0.5` — в чистом venv резолвится в
   **kimi-cli 1.12.0** (а не 1.48.0, как на машине).
2. `kimi_cli/app.py` в 1.12.0: `KimiCLI.create(..., skills_dir: KaosPath | None = None)` —
   **единственное число**.
3. `Dockerfile` безусловно накатывал патч №2, переписывающий вызов на `skills_dirs=[...]`.

Итого в образе SDK звал `KimiCLI.create()` **несуществующим аргументом** → `TypeError` на первом
же вызове модели. Сборка этого не ловила: build-смоук дёргал только `build_user_content` (чистый
Python), а `prompt()` — никогда. А оркестратор по дизайну **мягко деградирует** (`orchestrator.py:343`:
ненулевой код → стадия пропускается, два `.docx` всё равно делаются). Значит в контейнере
one-pager просто **никогда бы не создавался**, и в логе оставался бы только 400-символьный хвост.

### Патчи

| Патч | Зачем | Нужен на 1.12.0 | Нужен на 1.48.0 |
|---|---|---|---|
| №1 `kimi_cli/utils/slashcmd.py`: `SlashCommand[F](` → `SlashCommand(` | `@dataclass(frozen=True, slots=True)` + PEP 695-generic → `TypeError: super(type, obj)`, падает сам `import` на Python 3.12 | да | да |
| №2 `kimi_agent_sdk/_session.py`: `skills_dir=` → `skills_dirs=[...]` | согласовать вызов с переименованным параметром | **нет — вреден** | да |

Патч №1 был описан только в README, патч №2 — только в `Dockerfile`. Установка строго по README
давала окружение без патча №2 (на 1.48 — нерабочее), а Docker применял патч №2 там, где он ломает
(на 1.12). Обе инструкции были неверны, каждая по-своему.

### ✅ Как исправлено

Зафиксирована пара, которую SDK **сам объявляет совместимой**: `kimi-agent-sdk==0.0.5` +
`kimi-cli==1.12.0` + `playwright==1.60.0` (та же версия, что в основном venv → общая ревизия
chromium в `ms-playwright`). Выбор согласован с владельцем: кастомный провайдер
(`KIMI_BASE_URL`/`KIMI_API_KEY`/`KIMI_MODEL_NAME`) поддержан в 1.12.0 ровно так же, как в 1.48.0 —
сверено по исходникам обеих версий, то есть апгрейд до 1.48 не был ничем вынужден.

- `lead_orchestrator_kimi/requirements.txt` — полный лок (транзитивные версии пересняты с чистого
  дерева 1.12: `kosong 0.42.0`, `fastmcp 2.12.5`, `mcp 1.16.0` — от дерева 1.48 они отличаются).
  Ставится **без `--no-deps` и без конфликтов резолвера**.
- `lead_orchestrator_kimi/patches/apply_patches.py` — **один** скрипт для Docker и локальной
  установки. Идемпотентен, есть `--check`. Патч №2 в нём **адаптивный**: имя параметра берётся
  **интроспекцией `KimiCLI.create`**, а не по номеру версии. На 1.12.0 он сообщает «правка не
  требуется» и не трогает рабочий вызов; если кто-то поднимет kimi-cli — сам применит правку.
  Именно эта проверка и предотвращает баг, который был в Docker.
- `Dockerfile` — ставит по локу и зовёт тот же скрипт; в смоук добавлен `apply_patches.py --check`,
  так что рассогласованный образ больше не соберётся.
- Локальный `.venv_kimi` пересобран с нуля по локу (старый сохранён как `.venv_kimi_bak_1.48`).

Проверено на пересобранном venv: `apply_patches.py --check` — зелёный; `from kimi_agent_sdk import
prompt` — импортится; `onepager_kimi` импортится и `build_user_content` работает; все пять kwargs,
которые шлёт стадия (`model`, `thinking`, `yolo`, `final_message_only`, `agent_file`), присутствуют
в сигнатуре `prompt()`; chromium рендерит PDF.

### Побочно найдено и исправлено
`pip` на Windows читает `requirements.txt` локальной кодировкой (cp1251) и падает
`UnicodeDecodeError` на кириллице в комментариях, если в первых двух строках нет PEP-263 куки.
В новый лок кука добавлена. ⚠️ **`lead_orchestrator/requirements.txt` этой куки не имеет** — в
Docker (локаль UTF-8) он ставится, а вот локальная установка на Windows упадёт. Одна строка.

### ✅ Исправлено: утечка окружения в сторонний SDK
Было (`orchestrator.py:103`): `env = dict(os.environ)` — то есть `kimi-cli` (сторонний альфа-пакет,
запускаемый с `yolo=True`, авто-аппрув вызовов) получал `ANTHROPIC_API_KEY`, `YANDEX_DISK_TOKEN`,
`DADATA_TOKEN`, `CHECKO_TOKEN`, `FIRECRAWL_API_KEY`. Стадии нужен ровно один ключ — свой.

Стало: **белый список** (`_KIMI_ENV_ALLOW`) — ключ/endpoint/модель плюс инфраструктура, без которой
не стартуют python и chromium (Windows: `SYSTEMROOT`, `TEMP`, `LOCALAPPDATA`…; Linux: `HOME`,
`DISPLAY`, `XAUTHORITY`…; сеть: прокси и CA-бандлы). Список, а не «всё минус секреты»: при чёрном
списке каждый **новый** токен в окружении утекал бы автоматически. `PYTHONPATH` намеренно не
пропускается — он подмешал бы site-packages основного venv в интерпретатор Kimi, а это ровно тот
конфликт `pydantic-core`, из-за которого venv и разведены.

Проверено прогоном: в подпроцесс уходит **27 переменных вместо 81**, ни один чужой токен не
доезжает, `PYTHONPATH` отсечён, а chromium в урезанном окружении по-прежнему рендерит PDF.

## 4. API-контракты

### 4.1. `orchestrator.py` → `onepager_kimi.py` (subprocess CLI) — согласован ✅
Вызов (`orchestrator.py:322-331`): `[KIMI_PY, KIMI_CLI, company_name, "--out", tmp]` + опционально
`--industry`, `--pain`; `cwd=KIMI_DIR`, `env=_kimi_env()`, stderr→stdout. Парсер
(`onepager_kimi.py:232-244`) все эти флаги имеет.

Контракт результата — «код возврата + файл на диске»: `_cli` возвращает 0 только если PDF > 5000
байт; оркестратор при ненулевом коде **не валит компанию**, а пропускает стадию. Таймаут (900 с) и
семафор (2) навешаны снаружи, при отмене процесс убивается — осиротевших chromium не остаётся.

⚠️ **Стоимость Kimi наружу не возвращается** (`return 0.0`): расходы на третий деливерабл не
попадают в учёт стоимости прогона.

✅ Исправлено: docstring рекламировал флаг `--inn`, которого в парсере нет (команда из документации
падала с `unrecognized arguments`). Пример приведён к реальной сигнатуре.

### 4.2. `onepager_kimi.py` → `kimi-agent-sdk 0.0.5` — сверен с установленным SDK ✅
По исходнику `_prompt.py:22-43`, а не по комментарию:
```python
async def prompt(user_input, *, work_dir, config, model, thinking, yolo, approval_handler_fn,
                 agent_file, mcp_configs, skills_dir, max_steps_per_turn, max_retries_per_step,
                 max_ralph_iterations, final_message_only) -> AsyncGenerator[Message, None]
```
Все пять kwargs, которые передаёт `onepager_kimi.py:211-213`, существуют и keyword-only.
`Message.extract_text()` на месте. **Проверено повторно на пересобранном venv (kimi-cli 1.12.0) —
контракт держится.**

Особенности:
- Нативного `system` в `prompt()` нет: системная инструкция доставляется **дважды** — префиксом в
  `user_input` и через `agent_file` → `kimi_agent/system.md`.
- `tools: []` в `kimi_agent/onepager.yaml` — осознанно: дефолтный агент kimi-cli тянет
  `kimi_cli.tools.web:SearchWeb/FetchURL`, которые у кастомного провайдера дают `InvalidToolError`
  ещё до вызова модели.

### 4.3. ⏳ Kimi → HTML → PDF — контракт текстовый и хрупкий
Это не API, а договорённость о формате ответа, держится на литералах:
- `_extract_sheet` (`html_to_pdf.py:48-63`) ищет лист **подстрокой `"width:800px"`** и балансирует
  `<div>` регуляркой. Модель напишет `width: 800px` (с пробелом) — извлечение провалится, сработает
  фолбэк, и в PDF уедет **весь ответ вместе с каркасом `x-dc`**. PDF при этом будет > 5000 байт →
  **код возврата 0, оркестратор считает стадию успешной**. Молчаливый брак, который контрактом
  «returncode + размер» не ловится.
- Шрифты грузятся из `fonts.googleapis.com` **в момент рендера**. В офлайн-контуре PDF отрендерится
  подстановочными шрифтами — тихо не по бренду. (Отдельная ирония: лист, который продаёт
  «суверенность и on-premises», сам ходит в Google за шрифтами.)

Рекомендация: после рендера валидировать результат (одна страница, есть ключевые блоки, нет
`x-dc`/`support.js`) и возвращать ненулевой код при провале. Шрифты — вшить локально.

### 4.4. ⏳ Живой вызов модели не покрыт
Docstring и README говорят «не хватает endpoint провайдера», при этом рабочий endpoint прописан
дефолтом в трёх местах. Одно из двух устарело. Build-смоук проверяет только `build_user_content`,
`prompt()` не дёргается никогда — именно поэтому сломанный Docker-образ и проходил сборку. Снимается
одним smoke-прогоном с реальным ключом.

### 4.5. Контракт против галлюцинаций (продуктовый)
`onepager_kimi.py:41-88`: блоки 1–3, 6, 8 передаются модели **дословно**, регалии спикера — только
из `SPEAKER_FACTS`. Причина в самом коде: в первых прогонах модель **выдумывала регалии живому
человеку**. Защищено **только текстом промпта** — пост-проверки, что в вернувшемся HTML нет
посторонних фактов о спикере, нет. Для документа, уходящему внешнему заказчику от имени
госкомпании, стоит добавить хотя бы проверку вхождения канонических строк.
