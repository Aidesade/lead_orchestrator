# Хост email-верификатора — бриф для DevOps

Выделенный VPS под SMTP-верификатор адресов (проверка существования ящика через
`RCPT TO`, письма не отправляются). Сервер покупается и оформляется на АО «ЦИТ РТ» —
значит, любой инцидент с него (спам-рассылка, утечка данных, абьюз) юридически —
инцидент ЦИТ РТ. Поэтому приоритет ТЗ — не «поднять сервис», а **не дать себя
взломать и ограничить ущерб, если взломают**. Два центральных раздела:
аутентификация и доступ (03) и настройка PTR/SPF (05).

## TL;DR

- Владелец сервера — ЦИТ РТ, поэтому спам или утечка с него = юридическая
  ответственность организации (ст. 18 ФЗ «О рекламе», 152-ФЗ). Все требования
  ниже — следствие этого факта.
- HTTP-API верификатора отдаётся наружу **только через reverse proxy с TLS**:
  allowlist по IP рабочего офиса + общий секрет в заголовке `x-reacher-secret`
  (клиент пайплайна его уже поддерживает — env `EMAIL_VERIFIER_SECRET`).
- SSH — только по ключам и только с allowlist; парольной аутентификации нет.
- Порт 25 — только **исходящий**; входящего SMTP и MTA на машине нет вообще.
- PTR и SPF вешаются на **отдельный технический поддомен** с жёстким `-all` и
  коротким TTL. Основной домен ЦИТ РТ и tatar.ru в схеме не участвуют — при
  компрометации хост нечем «легитимизировать» фишинг от их имени.
- На сервере нет ни секретов пайплайна, ни данных: stateless-сервис, пересоздаётся
  скриптом за 15 минут. Подозрение на взлом = снос и пересоздание, не лечение.
- Приёмка — готовым скриптом `verify_host_check.py` + внешний скан + чек-лист
  из раздела 07.

## 01 · Контекст — что за сервис

`email_verify.py` — Python-порт ядра open-source верификатора Reacher: один файл,
голый stdlib, без pip-зависимостей. Механика: MX-lookup → SMTP-сессия к чужому
серверу → `HELO`, `MAIL FROM`, `RCPT TO` → `QUIT` до `DATA`. Режим `--serve 8080`
поднимает Reacher-совместимый HTTP-API (`POST /v1/check_email`). С рабочей машины
пайплайн ходит в этот API поштучно; нагрузка — единицы запросов в минуту.

Выносим на сервер потому, что с офисной машины проба не работает: у её IP нет PTR,
принимающие серверы отвечают «cannot find your reverse» (по факту: из 69 компаний
подтвердились 5).

## 02 · Модель угроз — чем взлом подставляет ЦИТ РТ

Отправная точка: договор с провайдером и сам сервер оформлены на АО «ЦИТ РТ».
Ответственность за то, что происходит с этой машины, несёт владелец — вне
зависимости от того, кто фактически нажимал кнопки:

- **спам с сервера** — рассылка без согласия нарушает ст. 18 ФЗ «О рекламе»;
  жалобы в ФАС и штрафы адресуются юрлицу-владельцу, причём по каждой рассылке
  отдельно;
- **утечка данных** — адреса и ФИО ЛПР в трафике API — это персональные данные,
  ЦИТ РТ по 152-ФЗ выступает их оператором: при утечке обязан уведомить РКН в
  течение 24 часов, а с 2025 года за утечки ПДн действуют оборотные штрафы;
- **абьюз любого рода** (ботнет, майнер, скан чужих сетей) — претензии провайдера
  и потерпевших идут по договору, то есть опять к ЦИТ РТ.

Вдобавок хост — не анонимный VPS: наши же DNS-записи (PTR, SPF) публично объявляют
его почтовой инфраструктурой организации. Каждая мера ниже привязана к конкретному
сценарию:

| Сценарий после взлома | Ущерб | Контрмера |
|---|---|---|
| Рассылка спама/фишинга с IP, который наши PTR+SPF легитимизируют | письма «от инфраструктуры ЦИТ РТ» проходят SPF; претензии по ст. 18 ФЗ «О рекламе» | изолированный поддомен с `-all` и коротким TTL (раздел 05); rate-limit на исходящий 25; DNSBL-мониторинг |
| Утечка данных с хоста | адреса ЛПР — ПДн (152-ФЗ): уведомление РКН, оборотные штрафы | сервис stateless: на диске ничего нет, access-лог отключён; адреса ходят только по TLS (раздел 03) |
| Плацдарм для атаки на рабочую машину | на ней ящик @tatar.ru, реестр рассылки, токены CRM | сервер о рабочей сети не знает ничего: ни ключей, ни туннелей; связь — только входящий HTTPS с офисного IP |
| Ботнет/майнер, абьюз-жалобы провайдеру | блокировка VPS, разбирательства с юрлицом | минимальная поверхность, автообновления, алерт на всплеск исходящего трафика |

Общий принцип: **на сервере нечего красть и нечем подставить.** Никаких токенов
CRM, ключей почтовых ящиков, баз адресов. Единственная «ценность» хоста — его
IP-репутация и DNS-записи, и обе отзываются одной правкой (раздел 06).

## 03 · Аутентификация и доступ

### SSH — только администрирование

Парольной аутентификации не существует в принципе; брутфорс умирает не на
fail2ban, а на том, что проверять нечего:

```
# /etc/ssh/sshd_config.d/10-hardening.conf
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
AllowUsers verify-admin
X11Forwarding no
AllowAgentForwarding no
MaxAuthTries 3
```

Ключ ed25519 с passphrase, только у администратора. На уровне firewall 22/tcp
открыт исключительно с allowlist наших статических IP.

### Доступ к API — reverse proxy с TLS и двумя слоями аутентификации

Сам сервис аутентификацию не реализует (внутренний процесс за прокси), поэтому
её обеспечивает граница — nginx на 443:

1. **Слой 1 — сеть:** allowlist статического IP офиса; все прочие адреса получают
   отказ до какой-либо обработки запроса.
2. **Слой 2 — секрет:** общий токен в заголовке `x-reacher-secret` — тот же
   контракт, что у self-hosted Reacher (`RCH__HEADER_SECRET`). Клиент пайплайна
   поддерживает его из коробки через env `EMAIL_VERIFIER_SECRET` — правок кода не
   нужно. Секрет генерируется `openssl rand -hex 32`, живёт в конфиге nginx на
   сервере и в gitignored `env/.env` на рабочей машине; в репозиторий не попадает.

TLS — Let's Encrypt на имя технического поддомена: A-запись, нужная для FCrDNS
(раздел 05), одновременно обслуживает и сертификат.

```
# /etc/nginx/conf.d/verify.conf
limit_req_zone $binary_remote_addr zone=verify:1m rate=30r/m;

server {
    listen 443 ssl;
    server_name mail-verify.example.ru;
    ssl_certificate     /etc/letsencrypt/live/mail-verify.example.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mail-verify.example.ru/privkey.pem;

    # слой 1: только офисный IP
    allow 203.0.113.10;          # статический IP офиса — уточню
    deny  all;

    # слой 2: общий секрет (контракт self-hosted Reacher)
    if ($http_x_reacher_secret != "СЕКРЕТ_ИЗ_МЕНЕДЖЕРА_ПАРОЛЕЙ") { return 401; }

    location / {
        limit_req  zone=verify burst=5;
        proxy_pass http://127.0.0.1:8080;   # сервис слушает только внутри машины
    }
}

server {                          # 80 — только ACME-челлендж certbot
    listen 80;
    server_name mail-verify.example.ru;
    location /.well-known/acme-challenge/ { root /var/www/acme; }
    location / { return 444; }
}
```

Если статического IP у офиса не окажется — allowlist заменяется на «только
секрет + rate-limit»; это осознанное ослабление, лучше получить статический IP
у офисного провайдера.

Настройки клиента (рабочая машина, `env/.env`):

```
EMAIL_VERIFIER_URL=https://mail-verify.example.ru
EMAIL_VERIFIER_KIND=reacher
EMAIL_VERIFIER_SECRET=<тот же секрет>
```

## 04 · Hardening хоста

- **ОС:** Ubuntu 24.04 LTS минимальная, `unattended-upgrades` включён.
  VPS: 1 vCPU / 1 GB достаточно. Пакеты сверх базы: только nginx и certbot.
- **Никакого MTA:** Postfix/Exim не ставим, входящий 25 закрыт. Порт 25 нужен
  только исходящий (egress) — у провайдера он обычно закрыт по умолчанию и
  открывается тикетом; это первый вопрос до оплаты (в РФ Selectel/Timeweb
  открывают по заявке, AWS/GCP — практически нет).
- **Секретов пайплайна на диске нет:** env сервиса (`EMAIL_GUESS_HELO`,
  `EMAIL_GUESS_MAIL_FROM`) — публичные строки. Единственный секрет на сервере —
  токен API в конфиге nginx, и он не даёт ничего, кроме права задать вопрос
  «существует ли ящик».
- **Сервер одноразовый:** всё разворачивается скриптом (cloud-init/ansible),
  пересоздание с нуля — 15 минут. «Питомцем» машину не делаем.

### Firewall (nftables, default-deny на вход)

| Направление | Порт | Откуда/куда | Решение |
|---|---|---|---|
| ingress | 22/tcp | allowlist наших IP | allow |
| ingress | 443/tcp | allowlist офисных IP | allow |
| ingress | 80/tcp | интернет | allow (только ACME; nginx отвечает 444 на всё прочее) |
| ingress | 8080, 25, всё прочее | интернет | **drop** |
| egress | 25/tcp | любые MX | allow + `limit rate` (страховка от превращения в спам-пушку) |
| egress | 53, 443 | DNS, ACME, обновления | allow |

### Сервис под systemd с изоляцией

```
# /etc/systemd/system/email-verify.service
[Unit]
Description=Email verifier (Reacher-совместимый HTTP-API)
Wants=network-online.target
After=network-online.target

[Service]
DynamicUser=yes
WorkingDirectory=/opt/email-verify
Environment=EMAIL_GUESS_HELO=mail-verify.example.ru
Environment=EMAIL_GUESS_MAIL_FROM=verify@mail-verify.example.ru
ExecStart=/usr/bin/python3 /opt/email-verify/email_verify.py --serve 8080
Restart=always
RestartSec=3

# процессу нужны только исходящие TCP-сессии и ответы прокси
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
PrivateDevices=yes
ProtectKernelTunables=yes
ProtectControlGroups=yes
RestrictAddressFamilies=AF_INET AF_INET6
LockPersonality=yes
SystemCallArchitectures=native
CapabilityBoundingSet=

[Install]
WantedBy=multi-user.target
```

Даже при RCE внутри сервиса атакующий сидит под эфемерным пользователем без
capabilities, с read-only системой и без доступа к чужим каталогам.

## 05 · PTR и SPF

Принимающие серверы проверяют FCrDNS (PTR и A должны сходиться в кольцо) и SPF
домена из `MAIL FROM`. Наша задача — пройти эти проверки, **не вписывая боевой IP
в записи основного домена**: изоляция на уровне DNS — главная страховка от
сценария «взломанный хост шлёт SPF-валидный фишинг от имени ЦИТ РТ».

### Схема записей

Заводим отдельный технический поддомен (условно `mail-verify.example.ru`; вместо
`example.ru` — домен, который согласуем: НЕ tatar.ru и НЕ основной домен
организации):

| Запись | Где настраивается | Значение |
|---|---|---|
| A | DNS-зона домена | `mail-verify.example.ru → <IP>` |
| PTR (rDNS) | панель провайдера VPS | `<IP> → mail-verify.example.ru` |
| SPF (TXT) | на самом поддомене `mail-verify` | `v=spf1 ip4:<IP> -all` |

Порядок важен: сначала A-запись, потом PTR — многие провайдеры не дают поставить
PTR на имя, которое не резолвится обратно в этот IP. Эта же A-запись служит именем
для TLS-сертификата API (раздел 03) — одна запись закрывает и FCrDNS, и HTTPS.

### Решения, которые прошу выдержать

- **`-all`, а не `~all`:** жёсткий fail. SPF-валидную почту от поддомена может
  слать ровно один IP; всё остальное принимающие серверы бракуют, а не «помечают
  подозрительным».
- **TTL 300–600 секунд** на A и TXT поддомена: при компрометации записи
  отзываются одной правкой и умирают из кэшей за минуты, а не за сутки.
- **SPF корневого домена не трогаем.** IP верификатора не должен появиться ни в
  SPF основного домена ЦИТ РТ, ни тем более tatar.ru. Тогда максимум, что
  дискредитирует взломанный хост, — одноразовый технический поддомен, который мы
  отзываем и пересоздаём.
- `MAIL FROM` — ящик на этом же поддомене (`verify@mail-verify.example.ru`),
  `HELO` — имя из PTR. Оба значения уходят в env сервиса; без них SMTP-стадия
  сознательно не выполняется (fail-closed: представляться чужим доменом нельзя —
  SPF-отказ неотличим от «ящика нет»).

Бонус вне scope, но по теме: если на основном домене организации до сих пор нет
DMARC-записи (`p=quarantine`/`reject`) — стоит завести независимо от этого
проекта: она защищает бренд от подделки отправителя вообще.

## 06 · Детект и реагирование

### Мониторинг

- **Репутация IP** — главная метрика: cron-lookup по Spamhaus ZEN
  (`<reversed-ip>.zen.spamhaus.org`) каждые несколько часов, алерт при появлении
  в списке. Попадание в DNSBL — самый ранний признак, что с хоста пошёл чужой
  трафик.
- Алерт на всплеск исходящих соединений на 25/tcp сверх темпа пайплайна
  (счётчик nftables).
- Алерт на каждый SSH-логин и на 401-серии в логе nginx (перебор секрета).
- Живость: `systemctl is-active` + curl-проба API.

### Runbook при подозрении на компрометацию

1. Погасить VPS; снапшот диска — для разбора, не для восстановления.
2. Отозвать DNS: удалить TXT (SPF) и A поддомена, снять PTR. С TTL 300 записи
   умирают из кэшей за минуты.
3. Отозвать секрет API (`EMAIL_VERIFIER_SECRET`) и ключ SSH.
4. Пересоздать сервер из скрипта на **новом IP**, новый секрет, новые ключи.
5. Прогнать приёмку из раздела 07 заново.

Лечить взломанную машину не пытаемся — она одноразовая, пересоздание дешевле и
достовернее.

## 07 · Приёмка (Definition of done)

Диагностика уже написана — `verify_host_check.py` проверяет ровно те четыре вещи,
из-за которых проба обычно не работает:

1. На сервере `python3 verify_host_check.py --helo <имя-из-PTR> --from <ящик>`
   завершается «ГОТОВО» без единого ✗: исходящий 25 открыт, PTR есть и совпадает
   с HELO, SPF найден, контрольные сессии с живыми MX (nic.ru, Яндекс, mail.ru)
   нас принимают.
2. С рабочей машины проходит запрос и возвращается JSON с полем `is_reachable`:

   ```
   curl -s -X POST https://mail-verify.example.ru/v1/check_email ^
        -H "Content-Type: application/json" ^
        -H "x-reacher-secret: <секрет>" ^
        -d "{\"to_email\":\"postmaster@yandex.ru\"}"
   ```

3. Тот же запрос **без** заголовка секрета → 401; с IP вне allowlist → отказ
   до обработки. Проверить оба случая явно.
4. Внешний скан (`nmap` по IP из-за пределов allowlist): открыт максимум 80
   (отвечает 444), всё остальное — filtered/closed, включая 22, 443, 8080 и 25.
5. IP отсутствует в Spamhaus ZEN и основных DNSBL; в SPF корневого домена IP
   не появился.

После приёмки на рабочей машине в `env/.env`:
`EMAIL_VERIFIER_URL=https://mail-verify.example.ru`,
`EMAIL_VERIFIER_KIND=reacher`, `EMAIL_VERIFIER_SECRET=<секрет>` — пайплайн
начнёт ходить в новый хост без правок кода.

### Чего не делать

- Не открывать порт 8080 наружу и не отдавать API мимо прокси — без TLS и
  секрета он превращается в открытый оракул для чужих спам-баз.
- Не включать парольную аутентификацию SSH «на время отладки».
- Не вписывать IP хоста в SPF основного домена и не использовать tatar.ru
  в HELO/MAIL FROM.
- Не хранить на хосте ничего, кроме двух py-файлов, конфигов и секрета API.
- Секрет — только в конфиге nginx и в `env/.env`; в git не коммитить.

именем технического поддомена и IP офиса для allowlist.
